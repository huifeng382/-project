## 1. git 提交 / GitHub 推送的版本号命名规范（强制）

- 版本号格式：**大版本.小版本.更小版本**，如 `15.2.16`。
- **每次提交 = 一个新版本**：提交后版本号必须往后递推；commit message = **版本号 + 简短文字描述**（一句话说明改动，**最长不超过 20 个汉字**，2026-09-03 定），如：
  `git commit -m "15.2.19 - 更新触发文本示例"`。
- **⚠️ 含 merge 提交在内，一律带版本号（2026-08-28 教训）**：merge 提交也必须按 §1 命名（如 `16.2.2 - merge 远程生成方提交`），**不得**用 `merge: ...` 等无版本号的标题。曾把 merge 提交 `11fef19` 命名为 `merge: 合并远程生成方提交…`（无版本号）违反本规范；该提交已推送无法改名，仅记录教训，**后续所有提交（含 merge）严格执行**。
- 递推规则（按本次改动的**最高级别**递推）：

| 级别 | 版本号递推 | 触发条件 |
|---|---|---|
| **大版本**（major） | 大版本号 +1，小/更小清零（如 10.1.0 → **11.0.0**） | 代码**大幅度**修改；**数据**有改动；代码修改带来了**大幅度的改善** |
| **小版本**（minor） | 小版本号 +1，更小清零（如 10.1.0 → **10.2.0**） | 代码**小幅度**修改；小幅度**加入新的代码文件** |
| **更小版本**（patch） | 更小版本号 +1（如 10.1.0 → **10.1.1**） | 加入**临时文件**；**修改 bug**；**修改文本文件**（含本文档） |

- 一次提交同时含多级改动时，取最高级别递推。
- **⚠️ 版本号必须单调递增，绝不回退（2026-08-28 教训）**：大版本升过后（如 16.0.0），后续提交从该版本继续（16.0.1 / 16.1.0 / 17.0.0），**不得再使用低于已用过的版本号**（曾错把 16.0.0 之后的提交标成 15.5.5/15.6.0，已重排修正）。提交前先看 `git log --oneline -3` 确认当前最新版本号。
- **版本号延续 GitHub 既有编号（不重新起算；`10.0.0` 仅是格式举例）**：
  最近一个按本规范命名的提交 = **`15.2.16`**（commit `f8064ce`，2026-08-26，已推送 GitHub）。
  **下一提交从 `15.2.17` 起**，按上表递推规则递增；当前版本以 §5 版本记录最新行为准。
- 注：2026-08-26 曾有 3 个未按版本号命名的过渡提交（`864b6e4` feat / `3b7727d` chore / `70d34a0` docs，均已推送），**不计入编号**；自 15.2.17 起严格执行。

## 5. 行为约束（对 AI 助手，强制）

- **方案先行，先问后改**：每次对某个问题给出解决方案时，**先给出方案（含改动清单/预期影响），不要自动执行修改**，等待用户明确同意后再动手。
- 例外：用户已明确指示执行的操作（如「直接跑」「修改」），或纯只读操作（查询、分析、读取），不在此限。
- 若方案涉及代码/文件改动、重跑实验、提交推送，一律先列清单询问。
- **长任务汇报规则**：用 SSH 启动测试/训练后，若预计等待 **>30 分钟**，**不要定期汇报进度**——只需确认程序已启动运行，并**附上检查命令**让用户自查；仅在任务完成时汇报结果。

- **数据分析必须先完整验证再下结论（16.11.25 定，强制）**：给出对数据的分析/结论前（规模/深度/覆盖率/分布/归因/可行性等），**先完整检查一遍、确认正确，再下结论**；不得凭抽样印象、单一口径、未核对的数据随口断言：
  ① **全量核对**：能用全量数据算的不用抽样（抽样须标注并复核全量）；引用任何数值前先复算；
  ② **口径确认**：结论所用量纲/口径（如深度 = X_ 宏级链 vs .tl 级联、晶体管 vs 门数）必须与对比对象（训练侧/Rust 侧）一致并写明，不一致不得直接比较；
  ③ **交叉验证**：关键结论用两种独立方式/脚本核对（如模板级 + 候选级），矛盾时以更贴近使用域的实测为准；
  ④ **自查清单**：下结论前自查——是否被全量数据支持？口径是否一致？是否与既有记录冲突？冲突时先复核旧记录，不得直接否定或沿用；
  ⑤ **证据不足标「待复核」，不下定论**：证据不足时明确标注「待复核」，不写进 spec/结论正文当定论（教训：16.11.23 未核对 Rust 候选实测就按模板级深度把 DEPTH_MIX 定为「深度 OOD」并写入锚定表 ★ 深度档，16.11.24 被 1135 个 dut 网表候选实测（0% >6）推翻，需撤回并修正）。

- **给命令的粒度：一轮一步，块内一次给齐（2026-09-18 定，强制）**：给本地/服务器命令时，**一条回复只给一个命令块**。同一块内，凡**不依赖本步回复结果**的命令一律**一次给齐**（若干条单行连续排列即算一块），不要把一个流程拆成多块、分多轮给。只有后续命令**必须用到本步输出**时（路径要先探、判断要先看、分支要按结果选），才留到下一轮。
  （教训：2026-09-18 诊断 AND2 走步门失效时，一轮里并列给了「探路 / truth 归属 / 起代理 / 重跑走步 / 停代理对照 / 回放」六个独立块，用户要反复分辨哪块先跑、哪块能一起跑。）
  与 §6.1 命令安全并用：块内每条仍是单行、≤~430 字符、不出现尖括号占位符。

## 6. SSH 插件复制粘贴补丁（@linxin666/dsh-ssh，2026-08-26 实测定稿）

**问题**：插件内嵌 xterm 把裸 Ctrl+C 硬编码为发送 ^C 并 preventDefault，Chrome 又不为 Ctrl+Shift+C 触发原生 copy → 终端无法复制；Ctrl+V 也被吞。

**补丁**：`~/.dsh/patch-dsh-ssh-copy.mjs`（幂等，按锚点 `new import_xterm.Terminal({` 定位，不依赖行号）→ 给终端挂 `attachCustomKeyEventHandler`：
- Ctrl+C / Ctrl+Shift+C（**有选中**）→ 复制选中文本，不发中断
- Ctrl+C（**无选中**）→ 照常发送 ^C 中断
- Ctrl+V（无 Shift）→ 放行浏览器原生粘贴

**维护规则**：
- **插件升级/重装会覆盖本补丁** → 升级后重跑 `node ~/.dsh/patch-dsh-ssh-copy.mjs` 恢复，再**硬刷新页面（Ctrl+Shift+R）**生效。
- 写 `~/.dsh/`（工作区外）需 `danger-full-access` 权限。
- 备份：`client.js.dshcopy.bak`。

### 6.1 命令安全（踩坑实录，SSH 操作通用）

1. **禁止 `pkill -f 'xxx'` / `pgrep -f 'xxx'` 匹配自身**：命令命令行里含 'xxx' 字样 → 正则匹配到执行命令的 shell 自己 → **自杀断连**。正确做法：
   - 精确进程名：`pkill -9 -x <进程名>`
   - 括号技巧：`pgrep -f '[t]l_opt_shadow_batch'`（正则不匹配字面 `[t]...`，只匹配真实进程）
   - 或直接用 PID：`kill -9 <pid>`（`ss -ltnp` / `ps aux` 查）
2. **日志文件名必须核对**：循环变量拼日志名时易错（如 `train_${d#v2}.log` vs `train_$d.log`——run 目录名与日志名前缀可能不同）。复制粘贴/生成命令前先 `ls` 确认实际文件名。
3. **长命令会被终端截断**：超长粘贴命令可能被截断 → 拆成短命令，或写成脚本文件上传再执行。
4. **长任务用 nohup**：`nohup ... > log 2>&1 &`，避免 SSH 超时/断连中断；启动后 `sleep` 几秒确认进程 + 日志头已写出再离开。
5. **给用户的检查命令必须复制粘贴即用**：无自杀式通配符、路径/文件名正确、输出明确（如 `echo "$d: $(...) epochs"` 带标签）。
6. **ssh_exec 超时**：单条命令默认有超时；重活放 nohup 后台 + 轮询日志，不在前台长 sleep。
7. **服务器训练必须设 `OMP_NUM_THREADS`（重要，2026-08-28 实测）**：torch 默认每进程用满**所有核**；多 run 并行（如 4 run）不设 → 4×24=96+ 线程挤 24 核 → load 飙到 40+、缓存构建和 epoch 全慢 3-5×（实测首建缓存 11h、epoch 迟迟不出）。**每 run 设 `OMP_NUM_THREADS=6`**（并发数 × 每 run 线程数 ≤ 核数；4×6=24 满负荷不抖动）。检查：`grep Threads /proc/<pid>/status`（应 ~19，非 33）。
